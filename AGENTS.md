# Design rules
TypeScript 7.0.2 defines expected behavior. `docs/references.md` and `docs/navigation.md` record where this tool deliberately differs; `docs/validation.md` explains how to compare against the pinned compilers.

- **One owner per decision.** Any rule TypeScript applies needs one owner here. Examples: lexical classes (line breaks, whitespace, BOM and shebang), comment and directive syntax, module indicators, symbol meanings, namespace instance state, file-name kinds and their case policy, path separators, pattern matching, supported inputs, and AST traversal and token spans. Owners name the TypeScript function they port in a doc comment. Before implementing or fixing such a rule, search for that name and for other code making the same decision, then extend the owner and route every copy through it; if none exists, create one and name its TypeScript function. Apply the rule inside the operations callers already use, not in a helper each caller must remember, and move the whole decision, not only the part a bug exposed: after line breaks moved to `pragmas`, its own whitespace and shebang checks still differed from the lexer, and a BOM-prefixed file silently dropped a dependency.
- **Same question, same owner.** Reuse an owner only where TypeScript asks the same question. A related concept gets its own operation: declaration spaces are not lookup meanings, and namespace instance state has three values, not two. Where TypeScript deliberately applies a narrower rule at one site, such as starting JSDoc collection only after CR or LF, keep it and comment why.
- **Failures stay failures.** Fall back to another parse only on a grammar mismatch, and treat a path as absent only on `NotFound`/`NotADirectory`. Report depth exhaustion, resource limits, and other I/O errors as failures, and keep each distinct until the code that decides the response: do not drop it with `.ok()`, `unwrap_or*`, or a wildcard match arm, or map it into a variant another layer tolerates, such as `Unsupported` in a dependency. A masked failure becomes a different successful answer.
- **Exact names.** Text used as identity (module specifiers, export and ambient module names, configuration and manifest keys, and file names) keeps its exact value. Conversions that substitute U+FFFD or drop data (`from_utf16_lossy`, `to_string_lossy`, a decoder that pushes `REPLACEMENT_CHARACTER`) are for messages; report a name they would change as `Unsupported` rather than letting distinct names merge.
- **Done means proven end to end.** A behavior fix is done when a test that fails without the fix passes for every input variant the rule distinguishes, asserting the final outcome (the AST, the `Project::load` result, or a query result) rather than a helper's or an intermediate value. Derive the variants from the TypeScript rule, not from these examples: each character class it separates (CR, LF, CRLF, U+2028, U+2029; space, tab, NBSP; a leading BOM), exact versus folded case, `/` versus `\`, ties, and each option-dependent state. For a limit, cover just under, at, and over it, and show that valid input whose final tree is shallow, such as a long flat list the parser explores speculatively, stays under it. Take expected outcomes from the pinned compilers, not from this tool's current output.
